## 2. 체크섬 감사

인수 메모의 사전 실측에서는 ZIP에 든 36개 파일이 `SHA256SUMS.txt` 기준으로 모두 일치했다고 기록되어 있다. 현재 `SHA256SUMS.txt` 자체를 제외한 목록 항목은 35개다.

기준선 커밋 직전 현재 작업 디렉터리에서 `shasum -a 256 -c SHA256SUMS.txt`를 다시 실행한 결과는 34개 OK, 1개 실패였다.

- 실패 파일: `validation/handoff_checks.json`
- 매니페스트 기대 SHA-256: `88b86f839b686d2c303b3d2fa9aee90a8b4450226dc79bc37868d33780a46cf6`
- 현재 SHA-256: `cde5c3d8dcb028a1c526382e38c98da1659ac80592056093a3291bef5b5fd29d`

`scripts/verify.py`는 성공 시 `validation/handoff_checks.json`을 다시 쓰도록 구현되어 있다. 파일 수정 시각과 내용도 네 STL 검증 결과로 갱신된 형태라서, ZIP 사전검사 후 기존 `.venv`에서 검증을 실행하는 과정에서 결과 파일이 재작성된 것으로 판단한다. 원 ZIP을 작업 공간에서 찾지 못해 매니페스트 기대 바이트를 복원하지 않았고, 인수 당시의 실제 작업 상태를 기준선으로 그대로 커밋했다. 이후 `requirements.txt`와 `references/SOURCES.md`도 의도적으로 수정되므로 `SHA256SUMS.txt`는 **원 전달물용 매니페스트**로 유지하며 현재 트리 전체의 재현성 검증 수단으로 해석하지 않는다.

## 3. 검증 환경 누락과 수정

원래 `requirements.txt`에는 다음 세 패키지만 고정되어 있었다.

```text
numpy==2.3.5
trimesh==5.1.0
manifold3d==3.5.3
```

`scripts/verify.py`는 `trimesh.Trimesh.split()`으로 단일 연결체를 검사한다. Trimesh의 이 경로는 그래프 백엔드가 필요하지만 `networkx`가 선언되지 않아, 세 패키지만 설치한 환경에서는 네 STL 검증이 그래프 백엔드 부재로 중단됐다. 기존 `.venv`에 `networkx==3.6.1`을 추가했을 때는 검증이 통과한다는 인수 실측을 재확인했다.

수정: `requirements.txt`에 `networkx==3.6.1`을 명시했다.

깨끗한 임시 가상환경은 시스템 Python 3.14.6으로 만들고 수정된 `requirements.txt`만 설치했다.

```text
numpy==2.3.5
trimesh==5.1.0
manifold3d==3.5.3
networkx==3.6.1
```

검증 결과:

```text
PASS: four connected, watertight STL solids; viewer payloads match; options off.
Browser interaction and visual accuracy still require review.
```

즉 네 STL 모두 닫힌 메시, 양의 부피·일관된 winding, 단일 연결체이며 HTML 내장 바이트와 파일이 일치한다. 외부 섀시와 거치대 체크박스도 기본 꺼짐이다. 이 스크립트는 WebGL 표시, 클릭·회전·다운로드, 실제 3D 프린트 성공을 검증하지 않는다.

## 5. 후속 구현 입력

### 동 번호

- 초기 UI: `미지정`, `302`, `324`, `420`, `직접 입력`
- 번호는 독립 명판 레이어로 구현한다.
- 직접 입력은 표시만 바꾸며, 해당 번호의 위치·형식이 검증됐다는 뜻으로 해석하지 않는다.

### 세대 식별과 상태

- 현재 설명상 층당 4세대, 10층이므로 실제 호수와 분리된 40개 내부 키가 필요하다: `01-A`~`10-D`.
- 각 키를 전면/후면/좌우 발코니 및 창 열과 명시적으로 연결한 매핑 테이블을 코드에 둔다.
- 외부 섀시 상태: `없음`, `부분`, `전체`.
- 냉방 상태: `없음`, `거치대만`, `실외기 포함`.
- 두 축은 독립이며 기본값은 모두 `없음`이다. 원래 창호·문·난간은 어느 선택에서도 삭제하지 않는다.
- 사용자 사진은 세대마다 후대 상태가 달랐다는 근거일 뿐, 40세대의 실제 상태표로 사용하지 않는다.

### 4색 재료와 출력

제안 재료 그룹은 최대 네 개다.

1. 본체 콘크리트·발코니 슬래브
2. 원래 창호·난간·어두운 틈
3. 유리 및 후대 외부 섀시
4. 에어컨/거치대·동 명판·선택 강조부

역사적 색과 출력용 식별색을 구분해 팔레트 교체가 가능해야 한다. STL은 색/재료 정보를 저장하지 못하므로 단색 호환용으로 남기고 4색 출력은 3MF를 우선한다. 표면 질감은 이미지 텍스처가 아니라 출력 축척과 노즐/레진 해상도에 맞는 얕은 양각으로 구현하고 최소 두 출력 방식에서 시험편을 먼저 검증한다.

### 생성 구조

현재 코드는 모든 섀시와 모든 거치대를 각각 하나의 전역 레이어로 합치고 네 조합의 융합 STL을 미리 만든다. 세대별 선택을 곱하면 조합 수가 폭발하므로 같은 방식으로 완성 STL을 사전 생성하면 안 된다.

필요한 구조 변경:

- `balcony()`가 층·세대 키별 선택 부재를 반환하도록 분해
- 기본 구조, 원래 창호, 세대별 섀시, 세대별 거치대/실외기, 동 명판, 재료 그룹을 별도 주소로 유지
- 구성 JSON 스키마를 정의하고 Python CLI와 뷰어가 같은 데이터를 사용
- 정적 뷰어에서는 선택 레이어를 즉시 표시하되, 다운로드는 색·부품 관계를 보존하는 3MF 조립을 우선
- 단색 STL을 만들 때는 선택 부재를 기본 구조와 다시 boolean union하고 기존 watertight·single-body 검증을 그대로 적용
